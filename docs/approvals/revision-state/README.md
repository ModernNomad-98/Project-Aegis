# Revision-state record store (C1.1a seed)

**What this is:** an append-only, data-only record of plan-revision/reopen/stop
state for three named plan items and of published candidate heads for this
change. It is governance record data, not policy. It grants no approval, makes
no plan revision, reopens nothing and plans no remaining work.

**Provenance status: UNVERIFIED.** No owner-authorised authority record for the
store exists yet (the plan's AUTH-STORE prerequisite, requested as owner
decision T24). The manifest therefore records
`authority_kind = "UNKNOWN"`, `binding_status = "UNVERIFIED"` and no
`authority_ref_id`. The checker treats an UNVERIFIED or ABSENT binding as
`REQUIRED_INPUT_UNAVAILABLE`: the store is displayable as UNVERIFIED and can
never yield a verified readiness count until that authority record exists.

## Layout

    manifest.json                                  index + digests + provenance binding
    items/aegis-plan-maturity-package.jsonl         plan item A history (revision 5)
    items/aegis-plan-post-delivery-2026-11-09.jsonl plan item B history (revision 7)
    items/aegis-plan-integrated-2026-11-10.jsonl    plan item C history (revision 2)
    changes/c1-1-b1-minimal-2026-11-10.jsonl        change ledger (zero published heads)

All files are UTF-8, LF, append-only JSONL except `manifest.json` (one JSON
object, regenerated by the holder after an authorised append).

## Plan-item event format

One JSON object per line, keys in canonical (JCS) order, with:

| Field | Meaning |
| --- | --- |
| `event_id` | stable sort key, unique and ascending within a file |
| `prev_event_sha256` | SHA-256 of the exact previous line bytes (UTF-8, without the terminating LF); `null` for the first event |
| `item_id` / `plan_id` | stable plan-item identity |
| `event_kind` | `REVISION_RECORDED`, `REOPEN_COUNTED`, `STOP_STATE_SET`, `LIFECYCLE_EVENT` |
| `revision_counted` / `reopen_counted` | booleans; `reopen_counted` is true only on the single allowed counted reopen |
| `stop_state` | `OPEN`, `WAITING_ON_OWNER`, `PARKED_UNMERGED` or `CLOSED` (on `STOP_STATE_SET`) |
| `authority_ref` | `{authority_kind: REGISTER_ENTRY\|OWNER_LINE_RECORD\|UNKNOWN, authority_ref_id, authority_ref_sha256, holder_role, holder_identity_ref}` |
| `evidence_refs[]` | cited records with `ref_id`, `ref_sha256` and optional `note` |
| `recorded_at` / `recorded_by` | ISO-8601 UTC Z seed/binding timestamp and the recording role |
| `note` | optional free-text explanation of the recorded event; never a substitute for evidence |

The seed events all carry the seed timestamp: the underlying historical
revision dates are not recorded in the cited evidence and are not invented.
`recorded_at` here means "recorded into this store at the binding", not
"the revision happened at this instant".

## Derivation (no stored count is trusted)

- `revision_count` = number of `REVISION_RECORDED` events.
- `reopen_count` = number of events with `reopen_counted = true`; a second one is
  refused (`STATE_TAMPER_SUSPECTED`).
- `stop_state` = the value of the last `STOP_STATE_SET` event.
- The checker also validates the hash chain, the event-id ordering, the
  manifest's bytes/sha256/event counts/ids, and that the current file is an
  append-only **prefix of its git base version**. Removing a line, editing a
  prior line, decreasing a count, a second reopen, or a rename/restart reset is
  refused as state tamper.
- The prefix check is a **required input**. If no git base resolves for
  `--base-ref` (default `origin/main`), the store is blocked with
  `REQUIRED_INPUT_UNAVAILABLE` and `prefix_checks["__status__"] =
  "GIT_BASE_UNRESOLVED"`; the check is never skipped and never reported as run.
- Every manifest binding is compared to the re-derived state: a bound
  `revision_count` / review-head count may not exceed the derivation (a
  decrease is tamper, an append is not), a bound `reopen_used` may not be
  revoked, and a bound `stop_state` must equal the derivation. A stop-state
  transition therefore needs a refreshed manifest - which the per-file
  bytes/sha256 binding already requires for any append.

### A5 precedence for C (revision 2, not 1)

The earlier checkpoint intake snapshot recorded C = 1. The later recorded
revision-2 amendment lineage (plan REV2 header, rev-2 delta checkpoint,
amendment review) supersedes that intake snapshot for this counter, so the seed
is **2** and no decrease is implied. The precedence is itself recorded as
`C-0004` (`LIFECYCLE_EVENT`) in the item file. A Stage-C re-derivation
that yields 1 without a recorded authority event is INVALID /
`STATE_TAMPER_SUSPECTED` pending reconciliation - the checker re-derives the
counter from these files, so a silent edit cannot lower it.

## Change ledger

`changes/c1-1-b1-minimal-2026-11-10.jsonl` is seeded with **zero**
`HEAD_PUBLISHED` events: at authoring no head of this change had been published
outside the candidate. Its format is
`{seq (1-based, contiguous), head_sha (40 lowercase hex), kind (INITIAL|BATCHED_BLOCKING_FIX|FINAL_BLOCKING_FIX|EXCEPTION|RESYNC), exception_ref|null, counted_at, authority_ref}`.

The candidate head under evaluation is supplied to the checker as input and is
excluded from the review-head count by definition. The authoritative
published-head export governs at gate time; this ledger must be an **exact
mirror of every previously published head** in that export and never overrides
it. A truncated (prefix-only) ledger, an empty ledger when heads were
published, an extra head, or a disagreeing head is `STATE_TAMPER_SUSPECTED`:
an undercount is not accepted as "model lag". Live head history arrives only
under C1.1b.

## Manifest and digests

`manifest.json` carries `schema_version` (`aegis.revision-store/v1`),
`files[]` (`path`, `kind`, `id`, `bytes`, `sha256`, `event_count`,
`first_event_id`, `last_event_id`), `derived_counts_at_binding`,
`store_digest` and `provenance_binding`. It has **no `generated_at`** or
any other volatile field: its bytes are deterministic.

    store_digest = SHA-256(JCS({
      "schema_version": <manifest.schema_version>,
      "files": [{"path","bytes","sha256","event_count","id","kind"} sorted by path],
      "derived_counts_at_binding": {...}
    }))

The manifest's own bytes are not part of the digest (no circularity) and no
timestamp is included. Every file is re-hashed before the digest is accepted;
any mismatch is `STATE_TAMPER_SUSPECTED`. The binding is validated
separately and is never hashed as if it were verified.

    revision_state_sha256 = SHA-256(JCS({
      "schema_version": "aegis.revision-state/v1",
      "items": [{"item_id","revision_count","reopen_used","stop_state"} sorted by item_id]
    }))

This is the contract's VB-C06 derivation, computed from the plan-item records
only - never from the manifest bytes. A verdict whose VB-C06 differs is
`STATE_TAMPER_SUSPECTED`.

## Provenance binding (AUTH-STORE)

The seed binding is:

    authority_kind      = "UNKNOWN"
    authority_ref_id    = null        (nothing fabricated)
    authority_ref_sha256= null
    holder_role         = "programme-lead"
    binding_status      = "UNVERIFIED"
    unverified_reason   = "no owner-authorised authority record yet (AUTH-STORE / owner decision T24 not tabled)"

A VERIFIED binding requires exactly one of two evidence routes, re-checked at
gate time, never trusted from the manifest:

1. `REGISTER_ENTRY` - an approval-register entry appended **by the register
   holder under the register's own governance**; the register bytes must match
   `authority_ref_sha256` and the entry id must be present. This change does
   not append it and does not edit `docs/approvals/APPROVAL_REGISTER.md`.
2. `OWNER_LINE_RECORD` - a recorded owner-line/authority record cited by a
   repository-relative path and sha256, at that exact sha256. The cited file
   must itself be a closed-schema authority record
   (`aegis.authority-record/v1`: `record_id`, `authority_kind`,
   `status` = `ACTIVE`, `holder_role`, `scope{repo, change_id, head_sha,
   merge_target_ref}`). Any other repository file - including a page that
   happens to hash correctly - is not an authority record and downgrades the
   binding to UNVERIFIED with `STATE_TAMPER_SUSPECTED`.

A missing, edited or unresolvable cited record downgrades the binding to
UNVERIFIED and blocks readiness. `UNKNOWN` can never be VERIFIED.

## Custody (known gap, stated honestly)

`docs/approvals/` is **not** matched by the live gate-guard pattern applied to
this change (the pattern protects `scripts/`, root-level executables and
`tools/behavioral_eval_runner/`; all 47 C1.1a paths are unmatched). The
store's integrity in v1 is therefore **policy + append-only checker + git
history**, not CI protection: a repository administrator can still rewrite it.
That is the known custody gap recorded in the plan, not a claim of protection.
The approval register itself relies on the same append-only policy plus review.

## How to run the checker against this store

    python -m tools.aegis_verdict_gate --self-test
    python -m tools.aegis_verdict_gate check \
        --repo-root . \
        --verdict <verdict.json> --freeze <freeze.json> \
        --settlement <settlement.json> --head-history <head-history.json> \
        --stage-records-dir <stage-records> \
        --records-dir docs/approvals/revision-state

The store alone can be inspected with the checker's record reader:

    python -c "from tools.aegis_verdict_gate import records; s = records.load_store('.', base_ref='HEAD'); print([(k, v.revision_count, v.stop_state) for k, v in sorted(s.items.items())]); print(s.binding_status)"

See [the checker README](../../../tools/aegis_verdict_gate/README.md) for the
full output contract, blocker classes and limitations. `docs/approvals/APPROVAL_REGISTER.md`
remains read-only to this change and is never edited by it.

## Non-claims

This store is data. It does not approve, authorise, merge, reopen, revise or
plan anything; it does not make B1 enforcing; it does not satisfy AUTH-STORE; it
does not replace the approval register, the plan of record or any stage record.
