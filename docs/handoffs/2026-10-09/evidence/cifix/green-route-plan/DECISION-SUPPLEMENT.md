## What must change in the proposed architecture

An independent App check can attest to an authorization when it evaluates it. A green check alone does not force every merge through that evaluator, bind every mutable PR field at merge time, or withdraw success immediately when authority changes. The earlier packet's read/check-only controller is therefore insufficient for the stronger merge-time claims. A **merge broker** means a separate service that holds the only routine permission to update main and serializes each authorized merge; that is a substantial privilege and operational expansion.

The following is a design hypothesis for feasibility, not an installation plan:

1. Independently controlled authorization evaluator: authenticates the owner, reads immutable candidate bytes without executing them, and binds repository ID, PR, head, base ref and SHA, resulting tree, full path/mode/content manifest, policy revision, grant lifecycle and the applicable review/check evidence. Candidate workflow edits, copied labels/register text or a typed reviewer name cannot supply this authority. Signing/check credentials remain outside candidate execution.
2. A separate merger identity with repository `contents:write` and no routine administration permission, constrained by server rules to the authorized PR merge path. A proposed main update-restriction ruleset admits only that App, with **pull-request-only** bypass of that restriction. Separate rules/checks retain mandatory reviews and App-bound checks with no broker bypass. The settings administrator remains a trusted operator who can change the controls; that power is outside the ordinary-writer threat guarantee and must be explicit.
3. Because a PR can be retargeted while keeping H, another proposed ruleset denies the broker updates to every non-main branch, while explicitly preserving necessary proposal-branch writers. Also cover branch creation/deletion/rename and all destination patterns; an unintended excluded branch breaks confinement. This affects repository-wide work and cannot be hidden inside a one-PR approval.
4. One durable merge reservation covers the full tuple and serializes main updates, grant use and broker leadership. Every merge route—UI, REST, automation, other Apps and direct Git updates—must obey the chosen server controls. Strict checks alone are not proof of exact B/T binding. No automatic fallback through the owner's current administrator session is permitted by this proposal.

GitHub documents that classic actor push restrictions require an organization-owned repository. A public personal repository cannot simply adopt that familiar configuration. Repository rulesets document App bypass and a pull-request-only mode; whether the proposed multiple-rule composition actually confines this broker on this account is **UNPROVEN**. GitHub's documented merge queue availability is for public organization repositories and qualifying organization plans, so it is not a present shortcut for this User-owned repository. [Branch restrictions](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#restrict-who-can-push-to-matching-branches), [ruleset bypass](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository), [merge queue availability](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue).

The REST merge operation documents a head `sha` condition and `contents:write`; it does not expose an expected base-ref/base-SHA/tree condition. Thus an H pin plus a last-second GET is not an atomic B/T guarantee. Current documentation also describes an asynchronous merge API: acceptance can precede protection evaluation, so accepted/pending is not merged. A future design must select one API and reconcile its final outcome. A Checks run's `head_sha` is likewise not an atomic authorization transaction for every PR sharing that SHA. [Merge API](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request), [Checks API](https://docs.github.com/en/rest/checks/runs#create-a-check-run).

**Revocation has an unavoidable decision boundary to resolve.** A check can remain green while its issuer is unavailable. Event delivery, polling, receipt expiry and deleting a success later do not establish immediate denial. A proposed broker could serialize acknowledged revocation before dispatch, then treat the dispatched operation as pending until reconciled. It cannot promise to cancel a request already accepted by GitHub. “Revoke at any time until the observed merge completes” is not proven by these APIs. The owner must eventually accept a precisely described dispatch cutoff or the design must find a stronger primitive; this supplement selects neither. Expiry needs the same definition.

**Failover must fence actual GitHub authority.** A new leader epoch in a local database does not invalidate an old installation token or stop an already submitted request. A timed-out request stays reserved/unknown; never issue a second merge or reuse the grant until the original outcome is established. If fencing/draining cannot be demonstrated, the safe proposed recovery is to stop the merge lane while the ambiguity persists. Availability and recovery time then remain unknown. Token expiry, webhook arrival or a successful local crash test alone is insufficient.

**Required review is a separate obstacle.** Enforcing the new path for administrators can expose the existing requirement for one GitHub approving review. #682 presently has none. Agent D/F receipt comments do not automatically satisfy that platform rule. Feasibility must identify a valid independent reviewer account and prove its review counts while the broker still cannot bypass a missing/rejected review. A same-identity approval, fabricated approval, or silently reducing the required count fails the proposal. No reviewer is to be triggered by this planning task.

## Falsifiable proof gates

Scope of the threat model: protected-source merge authority and broker recovery, not production tenant data or a deployed live exploit. Assets are candidate integrity, owner intent, credentials and one-use history. Actors include a malicious writer/fork author, compromised candidate runner, wrong App, stale broker process and trusted settings operator. Boundaries are candidate→evaluator, owner→grant store, evaluator→GitHub checks, broker→branch updates, and operator→keys/rules. Unauthorized merge/key disclosure has HIGH consequence; exploit paths in the proposed system remain hypotheses. Outage without unauthorized merge is an availability failure.
