## Immediate decision: commission candidate research

**Recommended owner decision now:** commission source-only research that names at least one concrete authority source, freshness source, host and candidate operation, with documented terms and estimated costs for each. The comparison below is between architectural classes; it cannot justify an exact real grant. Research may inspect public/local documentation and existing repository records, and deliver a candidate matrix and a revised decision packet. It conveys no permission for credentials, source or host contact, claim writes, provider calls, deployment or target mutation. If the owner has not nominated candidates, the research should identify plausible names and report unknowns rather than silently select one for execution.

A later owner decision needs to select one exact approval source and consumption contract, a separately protected freshness source, one host and one allowed operation, and the evidence and billing authorities for that operation. A grant must identify its source record, revision, scope, expiry and lifecycle; the controller must authenticate these at the last dispatch boundary. A local journal, Git commit, PR approval, chat text or synthetic receipt alone cannot make a real one-use claim. The [design, sections 5.2 and 8.1](../design/resumable-control-plane-v1.md) requires atomic one-use consumption across *all* consumers and independent monotonic freshness or complete authoritative reconciliation. It also requires durable intent before contact, source receipt before dispatch, and denial on unknown, stale, conflicting or unavailable proof.

### Candidate authority sources

| Candidate | Operational terms and source of record | Benefits | Cost, failure mode and fit |
| --- | --- | --- | --- |
| GitHub approval record (issue, PR review/comment or register entry) | A named, authenticated owner decision is retrievable and reviewable. The owner would need to define exact record/revision, amendment and revocation semantics and every consumer's redemption path. GitHub review/merge approval by itself is not an atomic one-use claim spanning a manual consumer and the controller. | Familiar owner workflow; existing audit links and repository review. | API/network and rate/permission dependencies; lifecycle may span records and caches. An additional shared transactional redemption authority is still needed. Do not call a successful GitHub read a spend lock. |
| Local single-owner ledger | One controlled host could serialize its own controller attempts and replay exact claim receipts. Terms would have to forbid every independent manual/other-host use or route each through that one owner. | Small offline prototype and clear local crash tests. | Cannot prevent an outside consumer from using the same grant. Restore of an older valid ledger also needs an independent anchor. This is only viable as real authority if the *actual grant and operation* prove exclusive custody and fencing; neither is selected. |
| Transactional authority source shared by every consumer | A trusted source exposes authenticated, durable compare-and-consume by grant/use ID and effect key, with idempotent receipt lookup, revocation/expiry checks, and a protocol for uncertain acknowledgements. Manual and host consumers must use the same transaction boundary. | Directly addresses the cross-consumer race and gives a definitive one-use receipt if the source contract is proved. | New service, administration, credentials, availability, security and recurring/usage costs; its receipt still does not prove checkpoint freshness, target outcome or bill. Product and operational terms must be reviewed for the chosen provider. |

**Research hypothesis, not source selection:** favor a shared transactional consumption contract while manual or other-host consumers may exist, and test that hypothesis against named products and their documented guarantees. A GitHub record may carry the human grant while a separate transactional source consumes it, but those records would need authenticated binding and lifecycle synchronization. Do not implement or contact a service based on this comparison. If research establishes a genuinely exclusive single-owner operation, document its exclusion and fencing evidence and reassess the local-ledger option.

## Proposed sequence and later bounded grant packet

1. **Source-only candidate research (proposed now):** produce named candidates and citations for grant lifecycle, atomic consumption across manual/host consumers, independent freshness, host containment, operation receipt and billing, evidence handling, prices and terms. Record gaps and a recommended candidate for owner review. No live probe is included.
2. **Read-only contract inspection (separate scope after selection):** with a named source and host, inspect published contracts and, only if separately authorized, authenticated read-only state and host capability facts. No claim, reservation or redemption write is included. A documentation claim alone stays `UNPROVEN` until its selected source and host guarantees are tested.
3. **Disposable test-namespace claim proof (optional, separate explicit grant):** only if the selected source offers a suitable isolated namespace, approve exact claim/reservation/redemption writes, identity, test grant, effects, spend ceiling, cleanup and rollback limits before use. Test cross-consumer race, lost acknowledgement and lifecycle ordering there. This is not a production claim or target dispatch and cannot inherit the read-only grant.

Prepare each later owner grant **only after** its choices are filled with exact identifiers and source terms. Read-only inspection should check an independent freshness path and selected-host containment where the chosen read-only capabilities permit it, and inspect evidence and billing contracts using sanitized test receipts. It must stop before any production claim, target mutation or public dispatch. A result of `UNPROVEN` keeps the real gate closed.

Each grant request should name: exact source and, for a write proof, test namespace; source terms and principals; host and executable; operation descriptor and prohibited effects; precise files/commands; test data; credentials handling without exposing secrets; spend ceiling including retries and control calls; maximum active hours and line/file budget; evidence root/readers/retention; rollback or irreversibility; negative tests and acceptance reviewer; expiration and one-use limit; and stop rules for source outage, stale freshness, uncertain claim/billing, containment escape or scope drift. Record the owner's exact wording in the approval register and merge that reviewed governance record before implementation. A separate decision would still be needed for any real target operation or wider deployment.
