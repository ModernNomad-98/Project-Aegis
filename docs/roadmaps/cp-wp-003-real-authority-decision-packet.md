## Next decision: authenticated read-only source inspection

**Completed source-only step:** the [DynamoDB public contract inspection](cp-wp-003-dynamodb-public-contract-inspection.md) records the published limits, proposed write-ahead protocol and falsifiers for a single-Region conditional current head plus transactional grant/claim/receipt pattern. The [research matrix](cp-wp-003-named-candidate-matrix.md#independent-freshness-candidates) compares Firestore Native mode and explains why S3 Object Lock remains an optional archive hypothesis, **not a complete current-head proof**. DynamoDB remains the first inspection hypothesis, not a selection for execution. Its separately controlled writer, complete vector, pending-marker protocol, current read and lost-ack lookup remain unproved. The next decision must select an exact source/account/custody candidate and separately authorize any authenticated read-only inspection. If Google Cloud custody is preferable or AWS terms fail, inspect Firestore next. A GitHub-hosted Linux job remains a later bounded host hypothesis. The local ledger remains a narrow candidate only if every consumer can be proved to use one exclusive owner and fenced path.

**Terms:** a *grant* is the owner's scoped permission; *redemption* is the one-use transaction that consumes it; a *manual consumer* is a person or other tool able to initiate the same effect; *freshness* proves a checkpoint was not restored from an older valid state; a *receipt* is the source's durable answer about a claim or effect. A vendor transaction over its own records does not establish all of these end-to-end properties. [Definitions and evidence](cp-wp-003-named-candidate-matrix.md#reading-key-and-required-result) distinguish documented facts from proposed constructions.

| Inspection direction | Reason and benefit | Cost, drawback, and condition |
| --- | --- | --- |
| **DynamoDB first for a later authenticated inspection (proposed; separate grant)** | Single-Region conditional updates and transactions could bind a protected current head/pending marker and grant redemption/use receipt. This makes rollback and cross-consumer races testable. | Requires separate custody and a trusted writer that prevents arbitrary rewrites or deletes, plus a strongly consistent read of one complete head item or one transactional read of all required items. An AWS account, identities and permissions (Identity and Access Management, IAM), monitoring and retention would be needed later; reads, writes, storage and point-in-time recovery may bill. Its client request token lasts only 10 minutes, so durable receipt lookup and lifecycle rules still need proof. Exact price depends on Region, record size and retry volume. |

A Google Cloud project, service identity, monitoring and retention would be needed later. Daily free quotas are conditional; usage, storage, egress and point-in-time recovery may bill. A retried transaction callback cannot safely perform the target effect; current read and lost-ack lookup still need proof. |
| **Defer authenticated inspection** | Allows more time to settle owner, account and cost terms without contacting a source. | Leaves real authority unproved and CP-WP-003/004 BLOCKED. Public documentation alone cannot establish this project's cross-consumer and host guarantees. |

S3 Object Lock may later hold retained history, but it protects versions rather than establishing a monotonic current head. A complete S3 reconstruction would have to inspect every relevant version and delete marker, finish every listing page, prove completeness despite concurrent writes, and settle retention and cost. S3 supports single-object `If-Match` writes, but that does not atomically bind head, pending marker and receipt records. The S3 archive and GitHub-hosted job hypotheses add storage/request and private Actions allowance or possible billed usage respectively; exact cost needs a Region, retention period, repository plan and test volume. A separate grant would be needed before authenticated reads or host contact, and a further capped grant before any claim write. The [matrix](cp-wp-003-named-candidate-matrix.md#independent-freshness-candidates) gives primary source links, limitations and upkeep for each candidate. No $0 operating cost is assumed.

A later owner decision needs to select one exact approval source and consumption contract, a separately protected freshness source, one host and one allowed operation, and the evidence and billing authorities for that operation. A grant must identify its source record, revision, scope, expiry and lifecycle; the controller must authenticate these at the last dispatch boundary. A local journal, Git commit, PR approval, chat text or synthetic receipt alone cannot make a real one-use claim. The [design, sections 5.2 and 8.1](../design/resumable-control-plane-v1.md) requires atomic one-use consumption across *all* consumers and independent monotonic freshness or complete authoritative reconciliation. It also requires durable intent before contact, source receipt before dispatch, and denial on unknown, stale, conflicting or unavailable proof.

## Decisions and proof still missing

| Owner selection or contract | Minimum fact to pin before a real proof; denial condition |
| --- | --- |
| Exact authority source | Provider/product, account or repository namespace, immutable record identity/revision, authenticated owner and delegated principals, grant scope, lifecycle ordering, expiry clock, source availability and audit access. No selected source means no claim. |
| Atomic consumption | One-use transaction or reservation/redemption semantics, all controller/manual/other-host consumers, exact claim/effect idempotency, replay and lost-ack lookup, revoke/expire/supersede race ordering, authoritative receipt and failure behavior. A local reservation or two uncoordinated writes deny. |
| Freshness | Choose independent protected monotonic head *or* complete current-source reconciliation under design §8.1; pin separate custody, conditional commit/pending-marker protocol, complete run/effect/use/budget vector, watermarks, maximum proof age and dispatch-time renewal. A restored database or retained S3 version is not proof of the current head. Old, partial, unavailable or contradictory proof denies. A Git SHA or local head is insufficient. |
| Host and operation | Exact host identity, operating system/runtime and trust boundary; one operation descriptor, target, input and effect identity, allowed network/filesystem/process paths, bounded duration and cancellation/descendant fence. Unsupported containment or unproved nonexecution denies. CP-WP-004 remains a separate integration decision. |
| Evidence | Exact writer and verifier, root, classification, readers, encryption/key custody, immutable bytes and provenance, redaction/export rule, retention/review and incident hold. The CP writer cannot inherit BER policy by implication; missing access or tamper proof denies. |
| Billing and liability | Actual receipt and billing source, monetary units and pricing/version terms, per-attempt/control costs, cap, worst-case reservation, delayed/duplicate/contrary receipt reconciliation, dispute route and who pays. Unknown amount keeps worst-case liability and slot; no assumed zero charge or refund. |

## Proposed sequence and later bounded grant packet

1. **Source-only candidate research (complete):** [PR #290's matrix](cp-wp-003-named-candidate-matrix.md) records named authority, freshness, host and operation hypotheses, public terms, costs and gaps. It included no live probe and made no execution selection.
2. **Published-contract inspection (complete); authenticated inspection (next, separate grant):** the [DynamoDB public inspection](cp-wp-003-dynamodb-public-contract-inspection.md) records the transaction, read, custody and lost-ack limits without account access. Select an exact candidate and obtain a separate reviewed grant before inspecting authenticated read-only source state or host capability facts. No claim, reservation or redemption write is included. A documentation claim stays `UNPROVEN` until selected-source and host guarantees are tested.
3. **Disposable test-namespace claim proof (optional, separate explicit grant):** only if the selected source offers a suitable isolated namespace, approve exact claim/reservation/redemption writes, identity, test grant, effects, spend ceiling, cleanup and rollback limits before use. Test cross-consumer race, lost acknowledgement and lifecycle ordering there. This is not a production claim or target dispatch and cannot inherit the read-only grant.

Prepare each later owner grant **only after** its choices are filled with exact identifiers and source terms. Read-only inspection should check an independent freshness path and selected-host containment where the chosen read-only capabilities permit it, and inspect evidence and billing contracts using sanitized test receipts. It must stop before any production claim, target mutation or public dispatch. A result of `UNPROVEN` keeps the real gate closed.

Each grant request should name: exact source and, for a write proof, test namespace; source terms and principals; host and executable; operation descriptor and prohibited effects; precise files/commands; test data; credentials handling without exposing secrets; spend ceiling including retries and control calls; maximum active hours and line/file budget; evidence root/readers/retention; rollback or irreversibility; negative tests and acceptance reviewer; expiration and one-use limit; and stop rules for source outage, stale freshness, uncertain claim/billing, containment escape or scope drift. Record the owner's exact wording in the approval register and merge that reviewed governance record before implementation. A separate decision would still be needed for any real target operation or wider deployment.
