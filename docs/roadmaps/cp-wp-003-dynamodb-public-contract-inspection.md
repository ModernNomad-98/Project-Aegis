## Published contract that bounds the hypothesis

- In one AWS account and Region, `TransactWriteItems` atomically applies up to 100 actions on distinct items, with an aggregate 4 MB item limit. `Put` and `Update` can carry conditions; a transaction cannot both condition-check and update the same item. A failed condition, conflict, validation failure, or insufficient capacity cancels the transaction. `TransactGetItems` atomically reads up to 100 table items, also limited to 4 MB and one account/Region; it does not read indexes. These are source-record guarantees, not guarantees about an external effect. [Write API](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_TransactWriteItems.html); [read API](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_TransactGetItems.html).
- DynamoDB documents serializable isolation between transactions and individual `GetItem`/write operations. A multi-item `BatchGetItem`, `Query`, or `Scan` is only read-committed relative to a transaction as a unit and can mix before/after states. A strongly consistent `GetItem` of one complete head item, or one `TransactGetItems` for a multi-item vector, is the proposed verification read. Default eventually consistent reads can return old state after a successful transaction. [Transaction isolation](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html); [read consistency](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html).
- `ClientRequestToken` makes an otherwise identical write request idempotent for **10 minutes after the first request completes**. Changed parameters in that window cause `IdempotentParameterMismatch`; after it, the same token is a new request. A timeout or HTTP 500 on a write can leave the outcome unknown. A token is therefore a short retry aid, not the durable effect or claim identity. [Write API](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_TransactWriteItems.html); [error handling](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Programming.Errors.html).
- DynamoDB TTL deletion is asynchronous and can take days, so TTL cannot serve as the claim-expiry decision clock or promptly remove an authorization. Expiry must be checked in the conditional protocol against a selected trusted time source. [TTL behavior](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html).
- Point-in-time recovery restores an earlier state to a **new table**. IAM policies, tags, streams, TTL, deletion protection and PITR settings require separate setup on the restored table. AWS also warns that backup/restore or export during transaction propagation can contain only some changes from a recent transaction. A restored table is neither a current-head witness nor necessarily an atomic snapshot of the live transaction boundary. [Restore contract](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/pointintimerecovery_restores.html); [transaction backup/export warning](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html).

## Proposed write-ahead protocol — inference, untested

The independent authority account or broker owns a table identity and current project/run head. The identity must include an independently protected table incarnation pin, such as DynamoDB's creation-time [`TableId`](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_TableDescription.html); a table name or ARN alone cannot reject deletion and recreation under the same name. All records in one transaction reside in the same account and Region; a cross-account broker may call that table but cannot make a transaction span accounts. The head binds source revision, the complete project catalog/run-head vector, each run's source-head hash and watermark, monotonic epoch, effect/use/budget state, and pending operation keys. A stable operation key identifies one intended external effect and is never reused for different parameters. The local checkpoint writer has read/submit rights only through a constrained protocol; it cannot edit, delete, restore, replace, or reconfigure the trusted head. These custody statements are **requirements to prove**, not DynamoDB defaults.

1. **Read and qualify.** Read the complete protected head with a strongly consistent `GetItem`, or all required records in one `TransactGetItems`. Check independently pinned table incarnation, account, Region, epoch, source revision, exact catalog/run vector, source-head hashes and watermarks, and all unresolved pending markers against the local checkpoint. Equal sequence numbers with different hashes contradict; a later source watermark requires fetching and verifying every missing event before dispatch. If missing, stale, conflicting, or unavailable, deny dispatch. Validate the human grant's provenance, scope, expiry and revocation against the selected authority source; a local copy is insufficient.
2. **Write ahead before contact.** Submit one conditional `TransactWriteItems`: compare the expected head epoch/revision, advance the epoch, reserve worst-case liability and the operation slot, transition the grant from unused to claimed, and insert a uniquely keyed `PENDING` operation/claim record. Manual and controller consumers must use this same source transaction. Conditions prevent reuse and changed intent; the transaction stays within the published item/size/account/Region limits. No target call occurs until a positive source outcome **and** a fresh current-head check establish this exact pending record.
3. **Perform one bounded effect.** The selected host may contact the target only under its separately proven fence. The target operation must have its own durable idempotency or status/receipt lookup keyed to the pending operation. Source atomicity does not make that external contact atomic. Cancellation, host loss or timeout leave `PENDING` and worst-case liability intact until target and billing authorities settle it.
4. **Commit or reconcile.** On authenticated target receipt and billing evidence, conditionally transact from the exact `PENDING` head to a higher epoch and an immutable operation outcome/receipt, settling the liability only to a proven amount. If receipt is absent, contradictory or delayed, retain `PENDING` and deny another effect or refund. A terminal failure also needs proof that no effect or charge can appear later; otherwise it remains unresolved.
5. **Lost acknowledgement.** Persist the same operation key and request parameters before submission. If the source write acknowledgement is lost, read the authoritative marker and head with the required consistency; a single absent read does **not** prove a still-in-flight write failed. Reconcile the request through a bounded source protocol, or keep the slot frozen. Retry an identical transaction with the same client token only inside its documented window; after 10 minutes, no blind replay. Never contact the target twice based solely on token reuse, and never erase uncertain liability because a local process restarted.

This protocol needs an exact ordering rule for concurrent revoke, expiry and claim; a source time policy; a complete project catalog/run-head vector; and a dispatch-time freshness check that cannot race a later source change. A receipt row proves the source mutation, not target execution or cost. [The control-plane freshness contract](../design/resumable-control-plane-v1.md#81-mandatory-recovery-freshness-gate) remains the acceptance boundary.

## Falsifiers for a later separately authorized proof

| Probe | Required denial or evidence |
| --- | --- |
| Controller and manual consumer race one grant; revoke, expire or supersede during claim | Exactly one source claim can win; an invalid lifecycle or source outage denies both. A manual bypass falsifies one-use authority. |
| Crash or lose response before/after pending transaction, target contact, and final commit; wait beyond 10 minutes | Stable marker/head lookup distinguishes committed source state only when proven; any unresolved write or effect retains the slot and worst-case liability. No blind replay after token expiry. |
| Restore an older valid local checkpoint or swap the authority table with a PITR restore | An independently protected table-incarnation pin, epoch and source-head hashes must reject stale checkpoint or replacement table; the pin and cutover mechanism remain to be proved. A later watermark requires verification of all missing events. PITR or export mid-transaction must never be accepted as an atomic current witness. |
| Read head components separately, via eventual consistency, GSI, query or scan while a transaction changes them | Mixed/stale observations deny; only the proven complete strongly consistent item or transactional read path passes. |
| Try arbitrary `PutItem`, `UpdateItem`, `DeleteItem`, batch write, table restore/delete, IAM or broker-policy change with every runner/manual principal | All protocol-bypassing paths deny; an administrator or break-glass path with shared custody leaves independence unproven. |
| Conflicting, delayed or missing target receipt/bill; host child survives cancellation | No second dispatch or liability release until selected target, billing and containment proofs reconcile the exact operation. |

## Remaining gates and cost inputs

**Custody:** Select the exact AWS account, Region, table ARN and independently protected table-incarnation pin (`TableId` or an equivalently proved mechanism); source owner and separate broker/administrator; credential issuance, rotation, break-glass and trust boundary; human grant signer/revision/lifecycle ingestion; all controller and manual consumers; exhaustive IAM allow/deny and resource-policy tests; who can restore, swap, delete or reconfigure the table and how a cutover denies until revalidated; CloudTrail data-event and log custody. IAM supports DynamoDB action/resource/condition scoping, but `dynamodb:LeadingKeys` only restricts keys; it does not enforce monotonic or append-only semantics. The broker must constrain conditional mutations and deny bypass paths; even that remains unproved until policy and administrator/cutover tests pass. CloudTrail data events require configuration and are forensic evidence, not a synchronous head. [DynamoDB IAM actions](https://docs.aws.amazon.com/service-authorization/latest/reference/list_dynamodb.html); [condition examples](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/specifying-conditions.html); [cross-account access](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/rbac-cross-account-access.html); [CloudTrail events](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/logging-using-cloudtrail.html).

**Host and operation:** Select and probe the actual host identity, process/descendant containment, path ownership, credential exposure, network boundary, timeout and effect fence; exact target API, target idempotency/receipt/status semantics, cancellation and rollback; evidence root, writer, readers, encryption/key custody, retention and redaction; independent actual billing authority, cap and dispute path. Neither AWS documentation nor the synthetic CP-WP-003A tests prove these selected-environment facts. A source/account grant, disposable namespace and any write or provider probe need their own reviewed scope before use.

**Cost variables:** Reprice for selected Region, capacity mode, table class, item sizes and count, strongly consistent versus transactional reads, successful/canceled/conflicted transactions and retries, head polling, storage and retention, PITR, restore/export, data transfer, CloudTrail data events/log storage, broker compute/network calls, target and billing reconciliation. Test contention and throughput for a shared head item before selecting a capacity mode. Transactions consume two underlying reads or writes per item, including canceled transactions; PITR charges depend on table size and retention choices do not necessarily reduce that charge. No account, workload volume, spend ceiling or budget alert is selected here. [Transaction capacity](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html); [DynamoDB pricing](https://aws.amazon.com/dynamodb/pricing/).
