This is a candidate comparison for the [CP-WP-003 real-authority decision packet](cp-wp-003-real-authority-decision-packet.md), not a source selection, access grant, host probe, claim, or implementation approval. CP-WP-003 and CP-WP-004 remain [BLOCKED](resumable-control-plane-backlog.md#5-separate-work-packages-current-status). Public vendor documentation was inspected; no candidate account, service, host, credential, or endpoint was contacted.

## Reading key and required result

- **Grant:** the owner's scoped permission, with identity, revision, expiry, revocation, and permitted effect.
- **Redemption:** the one-use source transaction that lets exactly one authorized consumer spend a grant. A **manual consumer** is a person or separate tool that can initiate the same effect; it must participate in the same transaction boundary as the controller.
- **Freshness:** evidence that a valid-looking local checkpoint is the current one. An independent protected head or complete current-source reconciliation must reject an older restored checkpoint.
- **Receipt:** a durable answer identifying the completed claim or effect. A request acknowledgement, a local log, and a target outcome are different facts.
- **Fail closed:** with missing, stale, conflicting, or unavailable proof, the controller must deny dispatch and retain uncertain liability. [CP-WP-003A](cp-wp-003-offline-proof-proposal.md) tests this behavior with synthetic sources only.

The real candidate must bind a human grant to an authenticated, atomic one-use source action across *every* controller and manual consumer; prove an independent freshness path; and later demonstrate selected-host containment, evidence custody, actual effect receipt, and bounded billing. A vendor's transaction guarantee covers its own stored records, not those end-to-end properties.

**Comparison:** both services document atomic changes to their own records, so either could hold a shared grant/receipt. DynamoDB's conditional transaction and explicit short idempotency window make the recovery limit especially clear; Firestore's retrying callback is convenient but adds a side-effect hazard. Neither product makes a GitHub review or chat message a one-use grant. A GitHub record could be the *human decision input* only after its exact identity, revision, signer, amendment, and revocation rules are bound to the transactional source. The [existing packet](cp-wp-003-real-authority-decision-packet.md#candidate-authority-sources) explains why an uncoordinated local ledger does not cover manual consumers.

## Separate freshness candidate

**Amazon S3 Object Lock in compliance mode**, in a separately administered account and bucket, is a candidate *record store* for an independent freshness sequence. AWS documents that compliance mode protects a particular object **version** from overwrite or deletion until its retention date, including by the account root user. It also documents that a new version or delete marker can still be added over that protected version. [Object Lock contract](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html). AWS documents strong read-after-write consistency for successful `PUT` followed by `GET` or `LIST`. [S3 consistency model](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel).

**Proposed construction, not a documented end-to-end guarantee:** write a retained, uniquely named record for each committed checkpoint with sequence, predecessor hash, run/effect/use/budget vector, and pending/committed state; read and reconcile the complete relevant sequence before dispatch. Separate credentials and administration from the control-plane state database and redemption source. A restore of an old local database should then conflict with a later protected record. The candidate requires an exact commit/pending-marker protocol, completeness proof for listing and all effects, dispatch-time maximum proof age, retention and legal-hold policy, access controls, and negative tests for missing/delete-marker/contradictory versions. Object Lock protects stored versions; it does **not** by itself provide a monotonic latest pointer, a complete ledger, or atomicity with DynamoDB/Firestore or the target. S3 unavailability must deny dispatch.

**Cost and upkeep:** S3 bills storage and requests, including `PUT`, `GET`, and `LIST`; retained versions consume storage and cannot be removed early in compliance mode. [S3 pricing](https://aws.amazon.com/s3/pricing/). Exact cost and retention liability need a Region, object count/size, read frequency, and retention period. Keeping S3 in a separate AWS account reduces shared-administrator rollback risk for a DynamoDB choice, but both still depend on AWS; that distinction is an architectural inference, not proven independence. With Firestore, the providers differ, while account/credential custody still needs proof.

## Candidate host and bounded operation for a later proof

**Host candidate:** a GitHub-hosted `ubuntu-24.04` job in a disposable, owner-controlled private repository, with the exact runner image/tool versions recorded at a later proof. GitHub documents provisioning a new VM for each hosted job. [Runner model](https://docs.github.com/en/actions/how-tos/manage-runners/github-hosted-runners/use-github-hosted-runners). This is a plausible disposable host, **not** evidence of CP's process, descendant, path, or credential containment. Actual runner identity, image drift, source egress, token scope, and cleanup must be measured or denied. The user's paused VirtualBox/BER VM is not selected or resumed by this proposal.

The hosted job is a research candidate because each job starts on a fresh runner and a small marker effect can be observed without touching a product target. A self-hosted runner might offer more control over process fencing but would add setup, cleanup, and credential-custody work; neither host has been selected for execution.

**Operation candidate:** once separately approved, one non-sensitive local marker write under a job-specific temporary directory, with a stable effect key, expected file hash, and one workflow-artifact receipt. This would exercise a bounded effect and replay/receipt handling without an external product mutation. It is only a host/protocol proof; it does not satisfy CP-WP-004's selected real delivery integration or prove an external target's bill/receipt. A later grant would specify exact repository, workflow SHA, path, input, artifact retention, token permissions, process tree, timeout, cleanup, and source network endpoints before execution. GitHub Actions on a private repository consumes plan allowances and may bill after included minutes or storage are exceeded. [Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions). Existing repository CI costs do not authorize a new test run.

## Recommendation and next decision boundary

**Recommend DynamoDB as the first *research hypothesis* for a disposable claim proof**, with a separately administered S3 record store as the freshness hypothesis, and a GitHub-hosted Linux job for a later bounded host proof. The reason is the explicit conditional transaction and durable grant/use row pattern; it gives a direct falsifier for simultaneous controller/manual claims. This does not select AWS for execution. Firestore remains a credible alternative if the owner prefers Google Cloud or the AWS account/custody terms cannot be met. The specific AWS and Google pricing pages must be rechecked when a Region, account plan, and test volume are known; the figures here are planning inputs as viewed 2026-09-25, not a quote or spend approval.

The next owner packet must pin the exact source namespace, principals, immutable grant/revision, lifecycle and redemption API; identify **every** consumer; choose an independently protected freshness contract; and name the host, operation, evidence and billing authorities. It must request a separate read-only inspection grant before authenticated inspection, then a separate capped disposable write grant before any claim. Until a reviewed grant and proof establish those facts, source access, host contact, dispatch, and CP-WP-004 remain blocked.

The existing **4–8 active hour** candidate-research range is provisional planning time, separate from the selected **71–146 active hour** backlog subtotal. This research does not close or re-estimate a selected implementation row.
