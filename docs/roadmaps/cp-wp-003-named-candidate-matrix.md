# CP-WP-003 named candidate research matrix

**Status:** source-only research, 2026-09-25. This is a candidate comparison for the [CP-WP-003 real-authority decision packet](cp-wp-003-real-authority-decision-packet.md), not a source selection, access grant, host probe, claim, or implementation approval. CP-WP-003 and CP-WP-004 remain [BLOCKED](resumable-control-plane-backlog.md#5-separate-work-packages-current-status). Public vendor documentation was inspected; no candidate account, service, host, credential, or endpoint was contacted.

## Reading key and required result

- **Grant:** the owner's scoped permission, with identity, revision, expiry, revocation, and permitted effect.
- **Redemption:** the one-use source transaction that lets exactly one authorized consumer spend a grant. A **manual consumer** is a person or separate tool that can initiate the same effect; it must participate in the same transaction boundary as the controller.
- **Freshness:** evidence that a valid-looking local checkpoint is the current one. An independent protected head or complete current-source reconciliation must reject an older restored checkpoint.
- **Receipt:** a durable answer identifying the completed claim or effect. A request acknowledgement, a local log, and a target outcome are different facts.
- **Fail closed:** with missing, stale, conflicting, or unavailable proof, the controller must deny dispatch and retain uncertain liability. [CP-WP-003A](cp-wp-003-offline-proof-proposal.md) tests this behavior with synthetic sources only.

The real candidate must bind a human grant to an authenticated, atomic one-use source action across *every* controller and manual consumer; prove an independent freshness path; and later demonstrate selected-host containment, evidence custody, actual effect receipt, and bounded billing. A vendor's transaction guarantee covers its own stored records, not those end-to-end properties.

**Comparison:** both services document atomic changes to their own records, so either could hold a shared grant/receipt. DynamoDB's conditional transaction and explicit short idempotency window make the recovery limit especially clear; Firestore's retrying callback is convenient but adds a side-effect hazard. Neither product makes a GitHub review or chat message a one-use grant. A GitHub record could be the *human decision input* only after its exact identity, revision, signer, amendment, and revocation rules are bound to the transactional source. The [existing packet](cp-wp-003-real-authority-decision-packet.md#candidate-authority-sources) explains why an uncoordinated local ledger does not cover manual consumers.

**Unknown write outcome:** an absent receipt on one current read after a timeout does not prove the write failed; it may still commit. Keep the claim and liability unresolved and deny retry or dispatch until the chosen transaction and marker protocol can reconcile the outcome.

## Independent freshness candidates

The [control-plane design, section 8.1](../design/resumable-control-plane-v1.md#81-mandatory-recovery-freshness-gate) requires a current project catalog/run-head vector and monotonic epoch that the local journal/checkpoint writer cannot roll back. The trusted source must advance durably with protected effect/use/budget commits **or an unresolved write-ahead pending marker**; a checkpoint export alone leaves a gap. The source's current head must be checked again at dispatch. A grant-redemption receipt is not automatically this proof. These are proposed data and custody patterns, not documented end-to-end vendor guarantees.

| Candidate | Atomic current-head pattern (inference, untested) | Independent custody and read requirement | Crash, retention, cost and blocking gaps |
| --- | --- | --- | --- |
| **Single-Region Amazon DynamoDB conditional head, first contract-inspection hypothesis.** [Conditional writes](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/WorkingWithItems.html) compare the latest item; [transactions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html) can atomically change a head and write a pending marker or receipt. | A separately administered account or trusted broker must prevent the local writer from arbitrary head rewrite, delete, table restore/swap, or policy change. Read a complete head/vector item with a [strongly consistent `GetItem`](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html), or read every required item in one [`TransactGetItems`](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html); separate reads can mix transaction states. Never use a default eventually consistent read. Bind the exact run/effect/use/budget vector and epoch. | A lost write acknowledgement requires a stable operation-key marker/receipt read before retry; the transaction client token covers only 10 minutes. A restored table is a **new table**, not a proof that its contents are current. [PITR](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Backup-and-Restore.html) can retain up to 35 days and bills by table size; [request/storage/backup prices](https://aws.amazon.com/dynamodb/pricing/) vary by Region and load. [Multi-Region eventual-consistency (MREC) global tables](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/globaltables-CoreConcepts.html) use asynchronous replication, last-writer-wins conflict resolution and Region-local transactions; strongly consistent multi-Region (MRSC) global tables are separate and do not support transactions. Neither is this proposed single-Region proof. Cross-account custody, protocol enforcement and current-at-dispatch race tests remain unproven. |
| **Google Cloud Firestore Native mode server transaction, alternative inspection hypothesis.** Transactions are [atomic, retry on contention and fail offline](https://firebase.google.com/docs/firestore/manage-data/transactions); Google documents [serializable isolation at commit time](https://cloud.google.com/firestore/docs/transaction-data-contention). | A separately administered project or trusted broker must prevent arbitrary document rewrites, deletes, database restore/swap or policy change. Server libraries [bypass Firestore Security Rules and use IAM](https://docs.cloud.google.com/firestore/native/docs/security/rules-fields); a local writer with unrestricted server credentials would defeat independence. Read the current head and complete vector within the documented transaction/read contract. | Keep side effects out of the retrying callback. An uncertain commit needs a stable operation-key marker/receipt lookup; an offline or unavailable read denies dispatch. [PITR](https://docs.cloud.google.com/firestore/native/docs/pitr) retains up to 7 days and is separately billed; recovery is not a monotonicity witness. [Reads/writes/storage/PITR pricing](https://cloud.google.com/firestore/pricing) and retention need a project, Region and volume. Custody, read age, contention and crash-boundary tests remain unproven. |
| **Amazon S3 Object Lock compliance-mode versions, optional archive hypothesis only.** A [protected version](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html) resists overwrite/deletion during retention, but Object Lock alone is **not** a complete current-head or monotonic freshness proof. S3 also supports single-object [`If-Match` conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html); this must not be described as absent CAS. | A separately administered bucket could preserve historical evidence. Any proposed reconstruction would have to inspect **all versions and delete markers** for every relevant key, exhaust [paginated `ListObjectVersions`](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectVersions.html), prove a complete and stable watermark despite concurrent listing/writes, and verify the current version and retention. A normal `GET`/`LIST` is insufficient when a delete marker is current. | New versions and [unprotected delete markers](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-managing.html) can hide retained versions from normal reads. `If-Match` compares one current object's ETag; it does not atomically bind separate head, pending marker, grant receipt, and target effect. Concurrent delete/write can return conflict or not-found, and the complete-list/snapshot proof is unspecified. Retained versions incur [storage/request charges](https://aws.amazon.com/s3/pricing/) and cannot be removed before compliance retention ends. Do not promote this archive hypothesis to the required dispatch gate without a separately reviewed complete protocol and falsification. |

**Shared failure rule:** no candidate may advance the local state first and anchor only at export. A trusted writer would need to record a pending marker before uncertain effect/use/budget contact or atomically commit the corresponding protected head, then resolve crash/lost-ack outcomes without dropping liability. Any stale, missing, contradictory, unavailable, or incompletely listed proof denies dispatch. A database PITR window or S3 retained history helps forensic recovery but cannot itself establish the current head.

## Candidate host and bounded operation for a later proof

**Host candidate:** a GitHub-hosted `ubuntu-24.04` job in a disposable, owner-controlled private repository, with the exact runner image/tool versions recorded at a later proof. GitHub documents provisioning a new VM for each hosted job. [Runner model](https://docs.github.com/en/actions/how-tos/manage-runners/github-hosted-runners/use-github-hosted-runners). This is a plausible disposable host, **not** evidence of CP's process, descendant, path, or credential containment. Actual runner identity, image drift, source egress, token scope, and cleanup must be measured or denied. The user's paused VirtualBox/BER VM is not selected or resumed by this proposal.

The hosted job is a research candidate because each job starts on a fresh runner and a small marker effect can be observed without touching a product target. A self-hosted runner might offer more control over process fencing but would add setup, cleanup, and credential-custody work; neither host has been selected for execution.

**Operation candidate:** once separately approved, one non-sensitive local marker write under a job-specific temporary directory, with a stable effect key, expected file hash, and one workflow-artifact receipt. This would exercise a bounded effect and replay/receipt handling without an external product mutation. It is only a host/protocol proof; it does not satisfy CP-WP-004's selected real delivery integration or prove an external target's bill/receipt. A later grant would specify exact repository, workflow SHA, path, input, artifact retention, token permissions, process tree, timeout, cleanup, and source network endpoints before execution. GitHub Actions on a private repository consumes plan allowances and may bill after included minutes or storage are exceeded. [Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions). Existing repository CI costs do not authorize a new test run.

## Recommendation and next decision boundary

**Recommend source-only contract inspection of the single-Region DynamoDB conditional head plus transactional grant/claim/receipt pattern first.** Its conditional writes offer a concrete way to test both rollback freshness and simultaneous controller/manual claims, subject to separate custody and the design's pending-marker protocol. This chooses a document-review priority, **not AWS for execution, account access, resource creation, or a claim write**. Firestore Native mode is the alternative freshness and redemption hypothesis if Google Cloud custody is preferable or AWS terms fail. S3 Object Lock remains an optional retained-history archive hypothesis, not the proposed current-head gate. A GitHub-hosted Linux job remains a later bounded host hypothesis. Pricing pages must be rechecked when a Region, account plan and test volume are known; the figures here are planning inputs as viewed 2026-09-25, not a quote or spend approval.

The next owner packet must pin the exact source namespace, principals, immutable grant/revision, lifecycle and redemption API; identify **every** consumer; choose an independently protected freshness contract; and name the host, operation, evidence and billing authorities. It must request a separate read-only inspection grant before authenticated inspection, then a separate capped disposable write grant before any claim. Until a reviewed grant and proof establish those facts, source access, host contact, dispatch, and CP-WP-004 remain blocked.

The named-candidate research is complete. The **4–8 active hour** range provisionally estimates the next selected-candidate read-only inspection, separate from the selected **71–146 active hour** backlog subtotal. This research does not close or re-estimate a selected implementation row.
