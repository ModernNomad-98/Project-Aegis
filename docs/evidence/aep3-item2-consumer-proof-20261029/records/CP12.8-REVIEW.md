## 5. Guard review on the merged commit

### 5.1 Correct ordering

The guard is at gate lines **15–33**, immediately after `def fail` (line 11) and before
**every** retained-content read: the first `open()` is `open(MANIFEST, "rb")` at line 56,
the first site-file read is line 95, and `os.path.isdir(SITE)` — the call that follows a
directory link and caused the original finding — is line 43. It cannot be skipped by the
rest of the gate: everything below it is either a later `fail` or a success print. In the
workflow it is at lines 175–193 inside the verify step (157–277), before the upload at
line 278 and the publish at line 285, so a refused run cannot upload or publish.

### 5.2 The checks, and which are reachable

1. `os.path.islink(SITE)` — `lstat`-based. True for a symlinked directory, a dangling link
   and a link pointing anywhere. This closes the CP-12 finding. **Reachable**; S3 and E2 hit it.
2. `os.path.realpath(ROOT) != os.path.abspath(ROOT)` — catches a symlinked release
   directory or a symlinked ancestor component. `os.path.abspath` is built on the physical
   `os.getcwd()`, so a symlink above the checkout does not misfire; only components below
   the workspace can trigger it. **Reachable**; S4 hits it, and the branch review's P2/P3
   probes (same gate bytes) hit ancestor components.
3. `site_real != os.path.join(os.path.realpath(ROOT), "site")` — **unreachable** once
   checks 1 and 2 pass: `SITE` is not a link and `ROOT` resolves to its own absolute path,
   so `realpath(SITE)` is exactly `realpath(ROOT)/site`.
4. `os.path.commonpath([site_real, repo_real]) == repo_real` — **unreachable** once check 3
   passes, because `site_real` is then `<physical cwd>/docs/evidence/releases/<release>/site`
   and therefore inside `repo_real`. `ValueError` is a defensive fallback for an
   absolute/relative mix that cannot occur with the two absolute paths used here.

So the guard has **two reachable refusal messages**, not four observed behaviours. This is
not a defect: it is fail-closed redundancy of the same kind the gate already uses. But the
record's phrase "four distinct refusal behaviours" overstates what can be observed; the
accurate statement is two reachable refusals plus two invariants. No mutation that passes
checks 1 and 2 can reach checks 3 or 4; the matrix and the branch review's P1–P4 cases
confirm this empirically.

### 5.3 Failure interface — unchanged

Every refusal calls the pre-existing `fail()`: one `::error::` line on **stdout** and
`sys.exit(1)`. No new exit code, stream or format. No case in the required matrix wrote to
stderr. Refusals occur before the upload/publish steps, so a refused deploy job stops
before publishing.

### 5.4 No behavioural drift

The guard gate is **byte-identical** to the branch gate (5,569 B, `13e9c7ae…`), and the
only workflow difference from pre-merge main is the 20 added lines (proved by reverse
reconstruction). The allowlist, manifest grammar, per-file `islink`/`isfile` checks,
forbidden-material and CR-byte gates, and the aggregate recomputation are textually
unchanged. Empirically, S0/S1/S2/A0/E1 are byte-identical to the pre-guard outputs, and the
guard's S3/S4/E2 refusals are the only differences. The messages that changed on
already-failing inputs (dangling links) keep the same exit code; this review did not
re-run those probes, but the gate bytes are the same ones the branch review exercised.

### 5.5 Build mode and triggers are untouched

The hunk is inside the deploy job. Build mode is byte-identical to pre-merge main and has
no guard counterpart (CP-12.6 remains UNRUN). The workflow has **no push or pull_request
trigger**; `on:` is `workflow_dispatch` only (line 7), and the deploy job additionally
requires `inputs.mode == 'deploy'` (line 133). Committing or merging content cannot
publish; only a deploy dispatch can, and none was made.

### 5.6 Small observations (non-blocking)

* `repo_real` is computed before it is needed and is used only by unreachable check 4.
* `os.path.realpath(ROOT)` is called twice (condition and message); harmless.
* The check is static, not race-free (no `O_NOFOLLOW`). The threat model is committed
  content in a fresh checkout, so this does not create a new exposure.
* The S4 message prints the absolute runner path of the link target; consistent with the
  gate's diagnostic style, no secret involved.
* The guard checks `SITE` but, at this commit, not `MANIFEST`; see section 6.
