## 2. What the change does, and why

**The old form, and the defect in it.** The test pinned three `MISREAD_PAGES` (L27-L31 of the base file) and asserted that none appears as a `full-page-acceptance` event in the **committed index**. That is an assertion about a snapshot of a generated artifact, not about the rule the test exists to protect. It was true only while the committed index was itself stale. Since then `.claude/skills/file-upload-storage-architect/SKILL.md` legitimately earned a keeper row — `K-181W` (withdrawal) and `K-189` (full-page-acceptance), both at revision `e2a3e20b7c20ef8385b219b39c6405237163406f` — so every faithful rebuild carries a legitimate acceptance for that page and the absolute assertion fails. The index is right; the test's premise was stale.

**The new form, in one sentence.** The premise is **re-derived on every run**: for each named misreading, the committed index must carry **exactly the keeper table's rows for that page at the index's own `built_at_ref`**, and where the ledger records a row the page's effective event in `reader_pages` must be the ledger's **highest-stable-id row** — the reader's own rule — which folds the before-withdrawal and after-withdrawal distinction in **by the record, not by a hard-coded status**. Where the ledger records nothing, the assertion is still "no acceptance at all", exactly as written before.

**Why the class, not the instance.** Retiring the single stale entry would fix one page of three. The other two are still pending **by record**: `.claude/skills/database-backup-verifier/SKILL.md` carries only `L-006` (lost-commit) and `.claude/skills/scoped-approval-register/SKILL.md` carries no keeper row at all. The re-read sweep is aimed at exactly those pending pages, so **the first legitimate re-record for either page trips the same absolute assertion on the next rebuild**. Anchoring the case to the ledger fixes all three permanently and keeps the labelled ground-truth negative case that the test file's own docstring binds to D73 row 1.

**Q5 — Complexity justification: why is the machinery warranted, and what would be smaller?**

**The warrant, stated first.** The machinery is warranted because **the rebuild is otherwise blocked forever**. A faithful rebuild cannot pass a suite whose premise is stale: the committed index records what the ledger records, the repaired test asserts exactly that correspondence, and the old assertion denies it — so without this repair no holder can re-run the owed AEGIS-APR-115 rebuild green at any head, at any cadence, and the five-merge rebuild cadence stays stopped. This change is what lets the blocked pull request be re-run instead of waived (section 8).

**Why the added comparison is warranted, in kind rather than in size.** This is not new machinery: it is one comparison per named page, made against an oracle the repository already builds and already trusts — `build_index.find_table` at the index's own `built_at_ref`, plus the reader's own highest-stable-id rule. What the repair buys is a change of **kind**: the old form **asserted an absolute about a snapshot** — "this page carries no acceptance in the committed index" — a fact about a generated artifact at one moment, falsified by the next faithful rebuild; the new form **re-derives its premise on every run from the record that owns the fact**, so it stays true as the ledger legitimately grows. An absolute about a snapshot decays; a re-derivation does not. That difference is the entire justification for one more comparison, and it is why the smaller forms below do not work.

**What would be smaller — the two alternatives, named and rejected with reasons.** Both are genuinely smaller than the change taken, and neither is left unaddressed.

- **(a) Retire the stale `MISREAD_PAGES` entry** — drop the page from the pinned list and leave the assertion as it stands. **Rejected: it fixes one page of three.** Only `.claude/skills/file-upload-storage-architect/SKILL.md` is in the acceptance set at this head, so only it actually trips the assertion today; the other two are still pending **by record** — `.claude/skills/database-backup-verifier/SKILL.md` carries only `L-006` (a lost-commit row, which is not an acceptance), and `.claude/skills/scoped-approval-register/SKILL.md` carries no keeper row at all. The re-read sweep is aimed at exactly those pending pages, so **the first legitimate re-record for either of the other two would trip the same absolute assertion on the next rebuild** — the same failure deferred by one event rather than removed. It would also delete the labelled ground-truth negative case that the test file's own docstring binds to D73 row 1, which is removing a check rather than repairing one. (Recorded as ND2; the "one page of three" reading was measured independently at Stage B.)
- **(b) Pin a status string** — make the assertion compare against a hard-coded event kind, or against a pinned revision literal. **Rejected: it folds a before/after-withdrawal distinction into a hard-coded value rather than into the record.** Whether a page's effective event is the withdrawal or the acceptance that follows it is a property of the ledger's rows and of the reader's highest-stable-id rule over them — which is exactly why the repaired test reads the keeper table and `reader_pages` instead of a literal. A pinned string states the answer for one moment and must be re-pinned at the next legitimate event: the same decay as (a), one indirection later. It would also put an authored, acceptance-shaped constant into the test, which AC10 exists to forbid.

*Routing: **bounded check** — the routing the workflow names for this question where the answer is uncertain; here the bounded check has already been performed and is **discharged rather than owed**. It is E7's four-run proof (reproduced independently at Stage B for AC1, AC2 and the control) and E9's three negative controls (AC6, AC7 and AC8, each exit 1), and it is read-only and time-boxed by construction: four suite runs in a full clone, and three mutations of a scratch copy of the index, each restored byte-for-byte.
